## 3. Existing Time-Dependent Systems

### How Time Progression Operates in Existing Systems:

1. **Attack Timers (`AttackComponent.cs`)**:
   - Accumulates `attackTimer += Time.deltaTime` in `Update()`.
   - In tests: stepped via `ManualTick(float deltaTime)`.
   - Guarded by `isAttackEnabled`, `ownerEntity.IsAlive`, `ownerEntity.CanBasicAttack`, and `BattleManager.Instance.IsBattleActive`.
   - When `attackTimer >= effectiveInterval`, it triggers `BasicAttackProcessor.ExecuteBasicAttack(...)` and resets `attackTimer = 0f`.

2. **Movement Displacement (`MovementComponent.cs`)**:
   - Calculates per-frame position step: `moveDelta = direction.normalized * (CurrentMoveSpeed * dt)`.
   - In runtime: `dt = Time.deltaTime` in `Update()`.
   - In tests: `dt = customDeltaTime` in `ManualTick(float deltaTime)`.
   - Guarded by `isMovementEnabled`, `ownerEntity.IsAlive`, `ownerEntity.CanMove`, and `BattleManager.Instance.IsBattleActive`.

3. **Status Effects, Crowd Controls, Shields, DoTs (`EntityStatusController.cs`)**:
   - Driven by `Tick(float currentTime)`:
     - In runtime: invoked from `EntityStatusController.Update()` passing `CooldownManager.TimeProvider != null ? CooldownManager.TimeProvider.CurrentTime : Time.time`.
     - In tests: invoked manually by test runners passing test timestamps.
   - Buffs, debuffs, crowd controls, and shields expire when `currentTime >= ExpirationTime`.
   - DoTs check periodic tick eligibility via `status.CheckTick(currentTime)`.

4. **Skill Cooldowns (`CooldownManager.cs`)**:
   - Completely **passive / pull-based** (no frame tick).
   - On skill trigger, sets `endTime = CurrentTime + duration`.
   - On query (`IsOnCooldown` / `GetRemainingCooldown`), calculates `endTime - CurrentTime` on demand.

5. **Loot Tier Upgrades (`LootTierProgressionManager.cs`)**:
   - Passive timestamp comparison against `DateTimeOffset.UtcNow.ToUnixTimeSeconds()`.

## 4. Current Tick Authority

### Audit Questions & Answers:

- **Q1: Does the game currently have one authoritative gameplay tick?**  
  **NO.** There is no centralized `GameLoop`, `BattleLoop`, or `SimulationManager.Tick()`. Time progression is **decentralized across independent MonoBehaviour components** attached to each Entity.

- **Q2: Who owns that tick?**  
  - **In Runtime:** **Unity's native PlayerLoop** drives individual `MonoBehaviour.Update()` invocations directly.  
  - **In Tests:** The **Test Runner** (`Prototype01PlayTestRunner`) acts as the tick authority, calling explicit deterministic methods (`ManualTick`, `Tick(currentTime)`, `TickActiveCast`).

- **Q3: What objects currently receive deltaTime?**  
  - `AttackComponent` (receives `Time.deltaTime` in `Update()`, `deltaTime` in `ManualTick`).  
  - `MovementComponent` (receives `Time.deltaTime` in `Update()`, `deltaTime` in `ManualTick`).  
  - `Entity.TickActiveCast(float deltaTime)` (receives `deltaTime` only in tests; currently not called in runtime).  
  - `DamagePopup` (UI animation).

- **Q4: How are Attack timers progressed?**  
  Via `attackTimer += Time.deltaTime` in `AttackComponent.Update()` (or `ManualTick` in tests), firing when reaching `effectiveInterval`.

- **Q5: How are Movement timers progressed?**  
  Via distance displacement `CurrentMoveSpeed * dt` calculated per frame in `MovementComponent.Update()` (or `ManualTick` in tests).

- **Q6: How are other time-dependent systems progressed?**  
  - Cooldowns: Timestamp arithmetic on demand (`endTime - CurrentTime`).  
  - Statuses / Shields: `EntityStatusController.Update()` calling `Tick(currentTime)`.  
  - Progression: Unix epoch timestamps.

- **Q7: Is there already a shared tick mechanism suitable for SkillCastState?**  
  There is no global shared tick manager. However, the **established architectural pattern** for all entity-level combat behaviours is: **a MonoBehaviour attached to the Entity GameObject executing its slice of time progression in `Update()` during runtime, and exposing a deterministic `Tick(deltaTime)` method for test runners.**

- **Q8: Would adding `Entity.TickActiveCast(deltaTime)` to that existing mechanism preserve architecture?**  
  **YES.** Adding an `Update()` method to `Entity` (or a dedicated component on the Entity GameObject) that calls `TickActiveCast(Time.deltaTime)` when `IsCasting` preserves the decentralized component architecture, requires no global manager, and maintains 100% compatibility with test runner manual ticks.

## 5. Entity Tick Integration Point

We evaluated three potential integration points for runtime cast ticking:

| Candidate Integration Point | Architectural Congruence | Complexity | Risks | Recommendation |
|---|---|---|---|---|
| **A. `Entity.Update()` on `Entity` base class** | **High** (matches `MovementComponent`, `AttackComponent`, `EntityStatusController`) | **Minimal** (~8 lines of code) | None; respects entity lifecycle and `IsCasting` state | **RECOMMENDED** |
| **B. `BattleManager.Update()` iterating entities** | **Low** (`BattleManager` currently has no `Update()`, does not tick attacks or movement) | **Medium** (requires managing hero/monster lists) | High; creates an artificial central loop for casts only | **REJECTED** |
| **C. `EntityStatusController.Update()`** | **Low** (conflates status/buffs with skill casting state) | **Medium** | Status controller uses absolute timestamps (`currentTime`), while Cast uses duration deltas (`deltaTime`) | **REJECTED** |

## 6. Proposed Cast Tick Call Chain

### CURRENT Call Graph (Runtime vs Test):

```
RUNTIME:
Unity PlayerLoop (Every Frame)
 ├──> AttackComponent.Update()       -> attackTimer += Time.deltaTime
 ├──> MovementComponent.Update()     -> displacement using Time.deltaTime
 ├──> EntityStatusController.Update()-> Tick(currentTime)
 └──> Entity                         -> [NO Update() -> TickActiveCast NEVER CALLED]

TEST RUNNER (EditMode / BatchMode):
Prototype01PlayTestRunner
 ├──> hero.Attack.ManualTick(dt)
 ├──> hero.Movement.ManualTick(dt)
 ├──> hero.StatusController.Tick(t)
 └──> hero.TickActiveCast(dt)        -> hero.CastState.Tick(dt) [CASE A]
```

### PROPOSED Call Graph (Unified Runtime & Test):

```
RUNTIME:
Unity PlayerLoop (Every Frame)
 ├──> AttackComponent.Update()
 ├──> MovementComponent.Update()
 ├──> EntityStatusController.Update()
 └──> Entity.Update()  [Natural host on existing Entity MonoBehaviour]
       │
       ├──> Guard: if (BattleManager.Instance != null && !BattleManager.Instance.IsBattleActive) return;
       ├──> Guard: if (!IsAlive || !IsCasting) return;
       │
       └──> Entity.TickActiveCast(Time.deltaTime)
             │
             └──> SkillCastState.Tick(deltaTime)
                   │
                   ├──> ElapsedTime += deltaTime
                   ├──> RemainingTime -= deltaTime
                   └──> if (ElapsedTime >= CastDuration) -> CompleteCast()
                         └──> SkillExecutor.ExecuteCastComplete(this)

TEST RUNNER (Unchanged):
Prototype01PlayTestRunner
 └──> entity.TickActiveCast(deltaTime) [Direct manual deterministic stepping preserved]
```

## 7. Architecture Risk

We audited against all Stop Conditions:

1. **Competing Tick Authorities**:
   - Introducing `Entity.Update()` does **not** create a competing tick authority. It follows the exact same pattern as `AttackComponent.Update()` and `MovementComponent.Update()`.
2. **Global Manager Duplication**:
   - Zero global managers (`CastManager`, `SkillTickManager`) are created or required.
3. **Async / Coroutine / Animator**:
   - No coroutines, async tasks, or animator events are used. Everything remains frame-deterministic.
4. **P07.8 Integrity**:
   - Shield and barrier pipelines remain completely untouched.
5. **CC, Rage, and Cooldown Authorities**:
   - CC authority remains strictly in `EntityStatusController`.
   - Rage authority remains strictly in `RageComponent` and `SkillExecutor`.
   - Cooldown authority remains strictly in `CooldownManager`.
6. **Pause & Death Handling**:
   - Guarding `Entity.Update()` with `BattleManager.Instance.IsBattleActive` and `IsAlive` ensures that paused battles or dead entities do not inadvertently progress casts.

## 8. Recommended Minimal Change

When authorized for implementation (in Phase 2.3 or Phase 3 runtime integration), the minimal change is:

In `Assets/_Game/Entities/Entity.cs`:
```csharp
protected virtual void Update()
{
    if (BattleManager.Instance != null && !BattleManager.Instance.IsBattleActive) return;
    if (!IsAlive || !IsCasting) return;

    TickActiveCast(Time.deltaTime);
}
```

This represents:
- **1 file to modify** (`Entity.cs`).
- **~7 lines of code**.
- **0 new files or managers**.
- **100% preservation of all existing tests**.

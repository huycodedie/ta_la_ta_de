## 1. Risk Statement

During the P07.9 pre-implementation audit, RISK-04 was identified as:
> *`SkillExecutionValidator` may fail to check `source.CanUseUltimate` when the skill being executed is an Ultimate skill, potentially allowing crowd-controlled entities (e.g. Stunned or Frozen) to bypass crowd control restrictions and cast Ultimate skills.*

This gate was established to comprehensively audit the current codebase, verify whether the check was missing or previously unified, validate all CC and permission semantics under automated and Play Mode conditions, ensure zero Rage leakage on validation failure, and run targeted regression suites.

---

## 2. Current Implementation Audit

Auditing `Assets/_Game/Combat/SkillExecutionValidator.cs` revealed that the validation was already unified and implemented during P07.9 Phase 0:

```csharp
// Lines 35-55 in Assets/_Game/Combat/SkillExecutionValidator.cs:
// 1.5 Validate CC Action Permission (P07.6 / P07.9 Phase 0)
bool isUltimate = request.Slot == SkillSlotType.Ultimate || (request.Skill != null && request.Skill.SlotType == SkillSlotType.Ultimate);
if (isUltimate)
{
    if (!source.CanUseUltimate)
    {
        failureReason = SkillExecutionFailureReason.SourceCrowdControlled;
        failureMessage = $"Source entity '{source.EntityName}' is crowd controlled and cannot use ultimate.";
        return false;
    }
}
else
{
    if (!source.CanUseSkill)
    {
        failureReason = SkillExecutionFailureReason.SourceCrowdControlled;
        failureMessage = $"Source entity '{source.EntityName}' is crowd controlled and cannot use skills.";
        return false;
    }
}
```

- **Slot Discrimination:** Checks `request.Slot == SkillSlotType.Ultimate` as well as `request.Skill.SlotType == SkillSlotType.Ultimate`.
- **Permission Facade:** Evaluates `source.CanUseUltimate`, which delegates directly to `EntityStatusController.CanUseUltimate`.
- **Reason Enum:** Correctly returns existing enum value `SkillExecutionFailureReason.SourceCrowdControlled`.

## 3. Ultimate Validation Flow

The complete execution flow from caller to resolution:

```
Caller (UI / AI / Test)
  │
  ▼
Hero.ExecuteSelectedSkill(SkillSlotType.Ultimate, target)
  │
  ▼
MindMethodManager.GetSelectedSkillForSlot(slot)
  │
  ▼
SkillExecutor.Execute(request)
  │
  ▼
SkillExecutionValidator.Validate(request)
  ├── 1. Source living & active check
  ├── 1.5 CC Action Permission check (isUltimate ? CanUseUltimate : CanUseSkill)  <-- [RISK-04 Check]
  ├── 1.6 Active Cast guard (source.IsCasting)
  ├── 2. Skill Definition existence check
  ├── 3. Active Mind Method match check
  ├── 4. Skill Unlock check
  ├── 5. Skill Selection for Slot check
  ├── 6. Target validity check
  ├── 7. Cooldown check
  └── 8. Rage requirement check
  │
  ├── [If Validation FAILS]:
  │     Returns SkillExecutionResult.CreateFailure(...)
  │     Raises EventBus.RaiseSkillExecutionFailed
  │     RAGE IS NOT CONSUMED.
  │     NO CAST / CHANNEL STARTED.
  │
  └── [If Validation SUCCEEDS]:
        Consume Rage (Step 2)
        Start Cast / Start Channel / Execute Instant (Step 2.5)
```

There are zero alternate execution pathways that bypass `SkillExecutionValidator.Validate()`. Both `Hero.ExecuteSelectedSkill()` and `Hero.ExecuteSkill()` construct a `SkillExecutionRequest` and route strictly through `SkillExecutor.Execute()`.

## 4. CanUseSkill Behavior

- `CanUseSkill` is evaluated strictly for non-ultimate skills (`request.Slot != SkillSlotType.Ultimate && request.Skill.SlotType != SkillSlotType.Ultimate`).
- In `EntityStatusController.cs`: `public bool CanUseSkill => !IsStunned && !IsFrozen;`.
- Tested in Automated TEST 11: A mock entity with `CanUseSkill == false` but `CanUseUltimate == true` blocks regular skills while allowing ultimates.

---

## 5. CanUseUltimate Behavior

- `CanUseUltimate` is evaluated strictly for Ultimate skills.
- In `EntityStatusController.cs`: `public bool CanUseUltimate => !IsStunned && !IsFrozen;`.
- In `Entity.cs`: `public virtual bool CanUseUltimate => StatusController == null || StatusController.CanUseUltimate;`.
- Tested in Automated TEST 01 and TEST 11: When `CanUseUltimate == true`, ultimate validation passes; when `false`, it fails with `SourceCrowdControlled`.

## 6. Stun Behavior

- **P07.6 Specification:** Stun disables movement, attack, normal skills, and ultimates (`CanUseUltimate == false`).
- When Stun is applied:
  - `hero.CanUseUltimate` becomes `false`.
  - `hero.ExecuteSelectedSkill(SkillSlotType.Ultimate, ...)` returns `Success == false` and `FailureReason == SourceCrowdControlled`.
  - Rage remains completely untouched.
- Verified in Automated TEST 02 and Play Mode Scenario B.

---

## 7. Freeze Behavior

- **P07.6 Specification:** Freeze disables movement, attack, normal skills, and ultimates (`CanUseUltimate == false`).
- When Freeze is applied:
  - `hero.CanUseUltimate` becomes `false`.
  - `hero.ExecuteSelectedSkill(SkillSlotType.Ultimate, ...)` returns `Success == false` and `FailureReason == SourceCrowdControlled`.
  - Rage remains completely untouched.
- Verified in Automated TEST 03 and Play Mode Scenario C.

## 8. Root Behavior

- **P07.6 Specification:** Root restricts movement (`CanMove == false`, `CanDash == false`), but preserves actions (`CanBasicAttack == true`, `CanUseSkill == true`, `CanUseUltimate == true`).
- Under Root:
  - `hero.CanMove` is `false`.
  - `hero.CanUseUltimate` remains `true`.
  - Ultimate skill executes successfully and deals full damage.
- Verified in Automated TEST 04 and Play Mode Scenario D.

---

## 9. Anti-CC Behavior

- **P07.6 / P07.9 Specification:** Active Anti-CC immunity (`StatusController.ApplyAntiCCImmunity`) blocks Stun and Freeze applications (`[CC:IMMUNE]`).
- Under Anti-CC:
  - Incoming Stun or Freeze fails to apply.
  - `hero.CanUseUltimate` remains `true`.
  - Ultimate skill executes cleanly without interruption.
- Verified in Automated TEST 05 and Play Mode Scenario E.

---

## 10. Rage Validation Ordering

- Per P07.9 Design Contract Rule P07.9-D02:
  > *Rage is consumed at Cast Start, strictly AFTER validation passes.*
- In `SkillExecutor.ExecuteSkill()`:
  - Step 1: `SkillExecutionValidator.Validate(...)`
  - Step 2: `rageComp.ConsumeRage(rageCost)`
- If an Ultimate is rejected due to Stun, Freeze, active casting, missing unlock, or invalid target, Step 2 is never reached.
- **Rage is never deducted and never requires rollback or refund logic.**
- Verified in Automated TEST 06, TEST 08, TEST 09, and Play Mode Scenario F.

---

## 11. Cast Behavior (Ultimate with CastTime > 0)

- When an Ultimate skill has `CastTime > 0`:
  - `SkillExecutionValidator.Validate()` runs first.
  - If rejected (e.g. caster is Stunned), cast does not start (`source.IsCasting == false`), and Rage is not deducted.
  - If accepted, Rage is deducted and `CastState.StartCast(...)` is called.
- Verified in Automated TEST 08.

---

## 12. Channel Behavior (Ultimate with IsChannel == true)

- When an Ultimate skill has `IsChannel == true`:
  - `SkillExecutionValidator.Validate()` runs first.
  - If rejected (e.g. caster is Frozen), channel does not start (`source.IsCasting == false`), and Rage is not deducted.
  - If accepted, Rage is deducted and `CastState.StartChannel(...)` is called.
- Verified in Automated TEST 09.
